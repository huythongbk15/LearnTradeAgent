## What the system is

A multi-agent crypto trading system in `src/trading_agent/`: agents produce
forecasts, a policy layer decides which strategy is promotable, a regime
router picks a strategy per market state, a shared-capital allocator sizes
positions, and an execution chain places orders with reconciliation.

17 canonical strategies on the allowlist. Execution is LLM-free on the hot
path; the LLM is enrichment-only.

## Known-unknown: is the pipeline deterministic

`scripts/check_wfo_determinism.py` was written to answer this and **was
still running when this document was written**. It compares two fresh runs
of the same spec. No prior test does this: `test_nested_wfo.py` calls
`run_nested_wfo` once in the entire file.

Everything downstream depends on the answer. If the pipeline is not
deterministic, no campaign re-run is worth its cost.

Observed cost structure while writing it: ~9 minutes per cell, not the ~25
seconds an early campaign suggested. `run_nested_wfo` runs a sensitivity
analysis (cost 2x, slippage stress, delay-1-bar, param neighbours) on
every fold, so a spec that looks minimal is four times the work it
appears. This is why a 10-hour single-strategy campaign and a 170-hour
full-registry re-measure are the wrong next steps without the determinism
answer first.

## The pattern to carry forward

Every result in this session that turned out wrong shared one shape: **a
check that could pass without the thing being true.**

- `Forecast.action` was mapped; the field does not exist, so signals were
  all zero and the run still reported 6/6 checks.
- A gate checked that metrics were *present*; the fabricators supplied
  every metric it asked for, so 38 of 44 stores passed.
- A campaign was launched without reading the sign-off that ranked every
  strategy.
- An abstained run (flat 0.00%) was compared against a negative buy-and-hold
  and produced a 32pp fake edge.
- `completed: 189, failed: 0` while strategies were being dropped.

Each was caught by running the thing or by an independent check, not by
reasoning. The durable lesson is that the evidence scripts now assert
`router_traded`, non-empty signals, attributable code, and campaign
coverage — and refuse to report a number when those fail.

## How this session got here

Six rounds of investigating AC14 — "does the adaptive router beat a fixed
incumbent out-of-sample?" — and the question moved upstream each time.

**Round 1** (synthetic, 12/12 checks PASS) measured methodology, not
efficacy. **Round 2** put it on real BTC/USDT data and hit three silent
fail-closed gates that returned a flat 0.00% run which read as "no edge"
rather than "nothing ran". **Round 3** diagnosed why everything lost —
cost drag, and a timeframe sweep that disproved the tidy conclusion.
**Round 4** removed the hand-wired regime map and posterior the round-2
run had used, and found a second silent pass: `Forecast.action` does not
exist, so signals were all zero and the run still reported 6/6 checks.
**Round 5** swept windows and found the router had abstained on three of
four; the first version of that script reported `EDGE_FOUND` by comparing
an abstained run against a negative buy-and-hold. **Round 6** audited the
policy store and found 2,690 promoted policies built from three literal
constants.

The failure shape was identical in every wrong result: **a check that could
pass without the thing being true.** Each was caught by running the thing
rather than reasoning about it. That is why the evidence scripts now
assert `router_traded`, non-empty signals, attributable code and campaign
coverage, and refuse to report a number when those fail.

Two cost estimates were also wrong by one to two orders of magnitude —
sensitivity analysis runs on every fold, and shorter folds produce *more*
folds — both found by measuring rather than assuming. The determinism
check exists because of them.

## Pipeline reproducibility — resolved

`scripts/check_wfo_determinism.py` ran the same spec twice into separate
output roots and compared aggregate metrics, per-fold params, trades,
return and Sharpe within 1e-9.

**Verdict: the measurements are deterministic.** Every metric matched
exactly across the two runs:

| metric | run 1 | run 2 |
|---|---|---|
| `median_test_sharpe` | 0.0 | 0.0 |
| `median_test_return_pct` | 0.0 | 0.0 |
| `n_outer_folds` | 3 | 3 |
| `total_test_trades` | 0 | 0 |

The four reported differences are all provenance, not arithmetic:

- `worktree_dirty` True vs False — the first run happened while this
  session was editing files
- `provenance_eligible` False vs True — a consequence of the above
- `study_manifest_id` differs — it contains `worktree_dirty`
- `study_manifest_path` differs — same reason

So the 14x spread between on-disk campaigns did not come from
non-deterministic computation. It came from the three pipeline bugs at
`a65ed29000` and from campaigns using different windows and
configurations.

**Caveat.** `total_test_trades` was 0 in both runs, so this establishes
determinism on an empty result — every metric zero, and any two runs
agree. It is a real result but a weak one.

A follow-up probe with `enhanced_ma`, which does trade, closed one fold
before being stopped:

| metric | fold_000, BTC/USDT 1h |
|---|---|
| total_return_pct | +7.489 |
| sharpe | 4.150 |
| max_drawdown_pct | 1.793 |
| total_trades | 9 |
| win_rate_pct | 55.6 |
| profit_factor | 7.82 |
| net_pnl | $748.94 |

That fold is not comparable to the campaign medians in
`ENHANCED_MA_MEASUREMENTS.md` (BTC median 0.000% over 104 cells) — it is
one test window, not a median, and the same finding applies: what this
strategy does depends on which window you look at. It is reproduced here
as evidence that the trading path is exercised, not as a performance
claim.

Determinism is therefore established for the measurement path and
unverified for a trading run. The residual gap is narrow, and closing it
with a full two-run comparison was estimated at ~4 hours against a
system that still has no strategy clearing promotion. Not started.

## Follow-up review — two generators the audit missed

Finding 1 — three generator scripts were missed

Yesterday's change removed fabricated scores from four generators named in
`POLICY_RETURN_AUDIT.md`: `run_tournament_shadow.py`,
`live_data_pipeline.py`, `t8a_cross_asset_stress.py` and
`t8a_tournament_validation.py`. Those were the four the audit *documented*.

There are more. `grep -rl "SelectionPolicyArtifact(" scripts/` finds six
generator scripts that build policy artifacts, and two were left behind:

| script | score written | code_sha | calls activate |
|---|---|---|---|
| `tournament_paper_trader.py` | `selection_score 0.50, median_oos_return_pct 0.05, median_oos_trades 40, 9/9 folds` | `"c" * 64` | **yes** |
| `run_s5_adaptive_campaign.py` | `selection_score` only | real `descriptor.code_sha` | **yes** |
| `evidence_ac14_windows.py` | passes through stored | passes through | yes (test fixture) |

`tournament_paper_trader.py` writes exactly the shape
`POLICY_RETURN_AUDIT.md` documents — `0.05` return, `40` trades, `9/9`
folds — and its memory notes record it running in **live** mode
(`TOURNAMENT_SHADOW_MODE=0`), reporting "15 promotions, Sharpe 1.58".

It is not exploitable: the gate refuses it. Verified directly —

```
code_sha for 'ma_crossover' does not match the canonical source
('cccccccccccc' vs '7fbb184a6c45')
```

So the outcome is a runtime `ValueError` partway through a live paper-trading
session rather than a clean refusal at import. That is the same shape as the
`build_tournament` bug the E2E run caught yesterday: self-contradictory
bootstrap code that only ever ran because fabricated scores let it through.

`run_s5_adaptive_campaign.py` passes the attribution check but emits only
`selection_score`, missing the OOS metric family, so it is refused by
`_require_measured_scores`.

Both need the same treatment as the four already fixed: no score block at
all, and no activation of an unmeasured policy.

The audit also missed these because it enumerated stores, not scripts. The
correct detection is a grep over producers, and that is what found them
now.

## What to do next

**1. Fix the two missed generators.** Half an hour, and it closes the class
of bug rather than one instance: grep every `SelectionPolicyArtifact(` in
`scripts/` and `src/`, and require each to either measure or carry none.

**2. Add the grep as a check.** The coverage invariant from yesterday
stops a campaign from under-reporting its strategies. Nothing yet stops a
*generator* from reintroducing a literal score. A short test that greps the
tree for a score block without the OOS metric family would have caught both
scripts, and would catch the next one.

That is the same lesson as the acceptance-evidence job added yesterday, one
level up: the fixture that violates the rule is the recurring failure, and
the durable fix is a check rather than a correction.

**3. Then, and only then**, the re-measurement in `HANDOVER_2026_09_28.md`.
Reproducibility is established and the gate chain works; what remains is
whether any strategy qualifies, and that is unchanged by either finding
above.
