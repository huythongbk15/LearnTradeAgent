## What the system is

A multi-agent crypto trading system in `src/trading_agent/`: agents produce
forecasts, a policy layer decides which strategy is promotable, a regime
router picks a strategy per market state, a shared-capital allocator sizes
positions, and an execution chain places orders with reconciliation.

17 canonical strategies on the allowlist. Execution is LLM-free on the hot
path; the LLM is enrichment-only.

## What happened this session

Started from "review the project and decide what to do next". The review
found the promotion pipeline had never verified that scores came from a
measurement, and following that through produced the rest.

### The finding

2,690 promoted policies carried `code_sha` values matching no source on
disk, with `median_oos_return_pct` drawn from three literal constants
(0.02 / 0.05 / 0.10) and `selection_score` a pure function of trade
count. Values were written straight into `SelectionPolicyArtifact.scores`
by four generator scripts with no measurement step.

Only **4 of 4,520** promotable policies are attributable to code that
exists. See `POLICY_RETURN_AUDIT.md`.

## Known-unknown: is the pipeline deterministic

`scripts/check_wfo_determinism.py` was written to answer this and **was
still running when this document was written**. It compares two fresh runs
of the same spec. No prior test does this: `test_nested_wfo.py` calls
`run_nested_wfo` once in the entire file.

Everything downstream depends on the answer. If the pipeline is not
deterministic, no campaign re-run is worth its cost.

Observed cost structure while writing it: ~9 minutes per cell, not the ~25
seconds an early campaign suggested. `run_nested_wfo` runs a sensitivity
analysis (cost 2x, slippage stress, delay-1-bar, param neighbours) on
every fold, so a spec that looks minimal is four times the work it
appears. This is why a 10-hour single-strategy campaign and a 170-hour
full-registry re-measure are the wrong next steps without the determinism
answer first.

## The pattern to carry forward

Every result in this session that turned out wrong shared one shape: **a
check that could pass without the thing being true.**

- `Forecast.action` was mapped; the field does not exist, so signals were
  all zero and the run still reported 6/6 checks.
- A gate checked that metrics were *present*; the fabricators supplied
  every metric it asked for, so 38 of 44 stores passed.
- A campaign was launched without reading the sign-off that ranked every
  strategy.
- An abstained run (flat 0.00%) was compared against a negative buy-and-hold
  and produced a 32pp fake edge.
- `completed: 189, failed: 0` while strategies were being dropped.

Each was caught by running the thing or by an independent check, not by
reasoning. The durable lesson is that the evidence scripts now assert
`router_traded`, non-empty signals, attributable code, and campaign
coverage — and refuse to report a number when those fail.

## How this session got here

Six rounds of investigating AC14 — "does the adaptive router beat a fixed
incumbent out-of-sample?" — and the question moved upstream each time.

**Round 1** (synthetic, 12/12 checks PASS) measured methodology, not
efficacy. **Round 2** put it on real BTC/USDT data and hit three silent
fail-closed gates that returned a flat 0.00% run which read as "no edge"
rather than "nothing ran". **Round 3** diagnosed why everything lost —
cost drag, and a timeframe sweep that disproved the tidy conclusion.
**Round 4** removed the hand-wired regime map and posterior the round-2
run had used, and found a second silent pass: `Forecast.action` does not
exist, so signals were all zero and the run still reported 6/6 checks.
**Round 5** swept windows and found the router had abstained on three of
four; the first version of that script reported `EDGE_FOUND` by comparing
an abstained run against a negative buy-and-hold. **Round 6** audited the
policy store and found 2,690 promoted policies built from three literal
constants.

The failure shape was identical in every wrong result: **a check that could
pass without the thing being true.** Each was caught by running the thing
rather than reasoning about it. That is why the evidence scripts now
assert `router_traded`, non-empty signals, attributable code and campaign
coverage, and refuse to report a number when those fail.

Two cost estimates were also wrong by one to two orders of magnitude —
sensitivity analysis runs on every fold, and shorter folds produce *more*
folds — both found by measuring rather than assuming. The determinism
check exists because of them.

## What to do next

Ordered by value per hour, not by size.

1. **Read the determinism result.** `/tmp/wfo_determinism.json` and
   `scripts/check_wfo_determinism.py`. Nothing else is worth doing until
   this is known. If non-deterministic, fix that first and stop.
2. **Re-measure one strategy on the fixed pipeline**, not the registry.
   `enhanced_ma` on SOL, the symbol where it looked least bad. This tests
   determinism in anger and produces the first citable post-fix number.
   Hours, not the 170 a full re-measure would cost.
3. **Decide the gate semantics explicitly.** `ENHANCED_MA_MEASUREMENTS.md §5`
   leaves the trade-count question open as three readings, and
   `GATE_SEMANTICS_AND_RERANK.md` records that p ≤ 0.20 was chosen with n
   as the binding constraint. Both are research decisions that no
   measurement settles.
4. **Only then** consider a registry-wide re-measurement, and with a
   campaign that writes its request list so the coverage invariant can
   verify it.

Do not do: re-measure all 17 strategies, promote anything from the
quarantined stores, or tune the selection score on the existing data.
There is no signal in it to tune against.
