# Handover — trading agent, 2026-09-28 to 2026-10-03

Six days, ~50 commits. One investigation that started as "review the project
and decide what to do next" and ended with a quantified answer to "can this
go live".

Every claim below traces to a commit or a document in this repository.
Where something was believed and then disproved, it is recorded, because
the corrections are the useful part.

## The answer

**No. The system cannot go live, and for a reason that is now measured
rather than suspected.**

`enhanced_ma`, the highest-scoring strategy in the registry, was run through
a real 32-fold walk-forward campaign on BTC/USDT daily bars:

```
median return   0.000%     trades: 5 across 23 folds
```

Widening the test window to 270 bars so that folds actually contain trades:

```
median return  -0.029%     trades: 35 across 28 folds
```

More trades produced a worse answer. That is what a strategy without edge
looks like when it is measured properly rather than on one window.

Then `stat_arbitrage_lo`, the first candidate that clears the trade-density
bar, ran the same campaign:

```
median return  -0.029%     trades: 45 across 28 folds
folds trading   20 of 28  ← density solved
folds positive    6 of 20  (30%)
win/loss ratio   0.50      break-even at 30% hit rate is 0.70
```

Frequency is solved for it. Payoff is not, and the gap is now quantified
at roughly 2x rather than described as an asymmetry.

Nothing was promoted. `data/promotion_store/` is empty by design, the
router abstains, and no policy reached ACTIVE.

## Timeline of findings, including the corrections

1. **2,690 fabricated policies.** Scored on three literal constants
   (`0.02 / 0.05 / 0.10`), `selection_score` a pure function of trade
   count. Quarantined; 43 stores under `data/policies_quarantine_20260928/`
   with a rollback manifest. → `POLICY_RETURN_AUDIT.md`

2. **Three WFO pipeline bugs**, one silently dropping strategies while the
   run reported success. 4,527 cells predate the fix. → `f4e2a91`

3. **`total_trades` counted only closed positions**, so a run with a +44%
   open position reported zero trades. → `0785502`

4. **No lookahead bias** — believed for two commits and then disproved. The
   engine fills at `open[i]` using `signals[i-1]`, which is correct. What
   differed between two engines was `fixed_position_pct` (0.10 default vs
   0.95 hardcoded), not fill timing. → `SIMULATOR_DISCREPANCY.md`

5. **12 of 17 strategies had been measured.** Five were skipped by my own
   probe on a "cross-sectional" label without testing them, and the entry
   counter missed every short entry — which inverted the density ranking.
   → `55e46ca`

6. **`stat_arbitrage_lo` trades in 71% of folds** where `enhanced_ma`
   managed 22%. The density constraint was necessary but not sufficient.

7. **Hit rate correction.** 70.7% was per-trade over a single window; the
   walk-forward figure is 30%. → `4fc0839`

## Why no strategy qualifies

The registry's strategies split on two axes, inversely:

| strategy | entry density | edge |
|---|---|---|
| `rsi`, `bbands` | dense — fill a 61-bar window | rejected, Sharpe -2.36 / -2.27 |
| `enhanced_ma` | sparse — 62% of windows empty | best measured Sharpe 1.19 |
| `stat_arbitrage_lo` | dense — 5 entries/window | hit rate 30%, payoff ratio 0.50 |

And the fold structure cannot absorb it. The spread gate needs enough folds
to be satisfiable (n≥14) and each fold needs to contain trades. At 61-bar
windows the file's entry count makes that impossible for the sparse
strategies; at 270-bar windows folds overlap, so the binomial's
independence assumption fails.

`plan_window_structure.py` maps the boundary:

```
 90-bar window (3mo)   31 folds  median 1 trade/fold  42% folds empty
180-bar window (6mo)   30 folds  median 1 trade/fold   3% folds empty
270-bar window (9mo)   28 folds  median 2 trades/fold  0% folds empty
```

Only 270 bars satisfies both, at the cost of fold independence. That tension
is a design decision, not a measurement.

## Five open decisions

None are measurement problems. All need a decision before more compute
buys anything.

1. **Gate semantics.** p≤0.20 and n≥14 were chosen in
   `GATE_SEMANTICS_AND_RERANK.md`. Both are judgement, not derivation.
   Loosening them would admit results the current ones reject, and nothing
   about the evidence base has changed to justify that.

2. **Fold independence vs fold count.** The 270-bar window that makes folds
   tradeable also makes them overlap. Either the binomial test accounts for
   correlated folds, or the window stays short and the sparse strategies
   stay unmeasurable. Currently undecided.

3. **Objective function.** `stat_arbitrage_lo` has a genuine hit rate and a
   losing payoff. Tuning an objective toward expectancy rather than win
   rate is the obvious next move, and it is unstarted.

4. **Registry composition.** The dense strategies were rejected for
   negative edge; the sparse one was approved but cannot fill a fold. A
   registry holding both kinds, with the gate applied to both, does not
   currently exist.

5. **`funding_carry` is unmeasured.** It needs `funding_rate` merged into the
   daily parquet via `scripts/merge_funding_rates.py`; the column exists in
   the hourly file only. The only outstanding item in the registry.

## The pattern worth keeping

Every wrong conclusion in this investigation had the same shape: **a check
that could pass without the thing being true.**

- `Forecast.action` was mapped; the field does not exist, so signals were
  all zero and the run still reported 6/6 checks.
- A gate verified that metrics were present; the fabricators supplied every
  metric it asked for, so 38 of 44 stores passed.
- A campaign ran without reading the sign-off that ranked all 16 strategies.
- An abstained run was compared against a negative buy&hold, manufacturing
  a 32-point edge.
- `completed: 189, failed: 0` while strategies were being dropped.
- `fixed_position_pct` was left at its default in a comparison where the
  other side hardcoded 95%, producing a 10x return discrepancy that read
  as lookahead bias.

Each was caught by running the thing rather than reasoning about it, and
the last two by checking the arithmetic after suspecting the code. The
durable response was to make the checks explicit — `router_traded`,
non-empty signals, attributable `code_sha`, campaign coverage, matched
capital deployment — so the next one fails a test instead of producing a
plausible number.

Two of these were found only because a cheap probe ran before an expensive
one. That ordering is the practical lesson: measure the small thing before
committing to the large thing.
